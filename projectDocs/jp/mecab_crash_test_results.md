# MeCab クラッシュテスト結果レポート

> **注意**: このドキュメントには、betajp-251206ブランチ（x64実験）からバックポートされた内容が含まれています。このブランチ（betajp-251206v4）は x86 ビルドを維持しているため、Windows x64環境に関する記述はこのブランチには当てはまりません。

## 調査日時

2025-11-27

## 調査方法

`findCrashingTests.ps1`スクリプトを使用して、各テストケースを個別に実行し、Windows fatal exception（アクセス違反）を検出しました。

## 調査手順

### 1. 前提条件

- Windows x64環境
- Python 3.13以上
- `uv`がインストールされている
- `scons.bat`が利用可能（推奨: Windows環境では`scons.bat`を使用）

### 2. スクリプトの準備

`jptools/findCrashingTests.ps1`スクリプトを使用します。このスクリプトは以下の機能を提供します：

- 各テストケースを個別に実行
- Windows fatal exceptionを検出
- テスト結果をMarkdown形式でレポート生成
- テストケースの情報（テキスト、入力、タブ文字の有無）を記録

### 3. 調査の実行

#### 基本的な使用方法

```powershell
# リポジトリのルートディレクトリで実行
.\jptools\findCrashingTests.ps1 -SkipInstall -StartIndex 0 -EndIndex 100 -OutputFile "crashing_tests_report.md"
```

#### パラメータ説明

- `-SkipInstall`: uv依存関係のインストールをスキップ（既にインストール済みの場合）
- `-SkipJtalkSync`: `scons jtalkSync`の実行をスキップ（既に実行済みの場合）
- `-StartIndex`: 開始インデックス（0ベース）
- `-EndIndex`: 終了インデックス（0ベース、排他的）
- `-OutputFile`: 出力Markdownファイルのパス

#### 実行例

```powershell
# 0-30の範囲を調査
.\jptools\findCrashingTests.ps1 -SkipInstall -StartIndex 0 -EndIndex 30 -OutputFile "crashing_tests_report_0_30.md"

# 30-100の範囲を調査
.\jptools\findCrashingTests.ps1 -SkipInstall -StartIndex 30 -EndIndex 100 -OutputFile "crashing_tests_report_30_100.md"

# 全範囲を調査（時間がかかる）
.\jptools\findCrashingTests.ps1 -SkipInstall -StartIndex 0 -EndIndex 2362 -OutputFile "crashing_tests_report_all.md"
```

### 4. スクリプトの動作

1. **テストケース数の取得**: `harness.py`と`nabccHarness.py`からテストケースを読み込み、有効なテストケース（`input`キーを持つ）をカウント
2. **インデックスマッピング**: 有効なテストケースのインデックスと元のインデックスのマッピングを作成
3. **個別テスト実行**: 各テストケースを`test_pass2_by_index`メソッドで個別に実行
4. **結果の分類**:
   - **CRASH**: Windows fatal exceptionが検出された場合
   - **FAILED**: 非ゼロの終了コードだが、クラッシュではない場合
   - **PASSED**: 正常終了した場合
5. **レポート生成**: 結果をMarkdown形式で出力

### 5. 結果の確認

生成されたMarkdownファイルには以下の情報が含まれます：

- **サマリー**: 総テスト数、クラッシュ数、失敗数、成功数
- **クラッシュしたテスト**: Windows fatal exceptionが発生したテストの詳細
- **失敗したテスト**: クラッシュ以外のエラーで失敗したテストの詳細
- **全テスト結果**: すべてのテストの結果一覧

### 6. トラブルシューティング

#### JSONパースエラー

一部のテストケースで、Unicode文字（特に点字文字や特殊文字）が含まれている場合、PowerShellの`ConvertFrom-Json`でエラーが発生する可能性があります。スクリプトはこのエラーをキャッチしてスキップします。

#### メモリ不足

大量のテストを実行する場合、メモリ不足が発生する可能性があります。範囲を分割して実行することを推奨します。

#### 実行時間

全テストケース（2362件）を実行する場合、数時間かかる可能性があります。範囲を分割して実行するか、特定のパターンに絞って調査することを推奨します。

### 7. 特定のパターンのテストを調査する

特定のパターン（例：タブ文字を含むテスト）のみを調査する場合：

```powershell
# タブ文字を含むテストのみを調査
.\jptools\runJpSmokeTests.ps1 -SkipInstall -TestFilter "test_pass2_tab_characters" -MaxTests 10
```

### 8. 結果の分析

生成されたレポートを分析して、以下の点を確認します：

1. **クラッシュパターン**: どのような文字や文字列がクラッシュを引き起こすか
2. **クラッシュ率**: 全体の何パーセントがクラッシュするか
3. **共通の特徴**: クラッシュしたテストに共通する特徴（全角スペース、括弧文字など）

### 9. 次のステップ

調査結果に基づいて、以下の対応を検討します：

1. **問題の特定**: クラッシュの原因となる文字や文字列の特定
2. **対策の実装**: 問題を回避するためのコード修正
3. **再テスト**: 修正後のコードで再テストを実行
4. **検証**: クラッシュが解消されたことを確認

## 実装状況

調査時点での実装:
- タブ文字を点字空白（U+2800, BRAILLE PATTERN BLANK）に置換

- `text2mecab.py`でタブ文字をU+2800に変換し、NFKD正規化でも変化しないことを期待

## 重要な発見

### 1. 点字空白（U+2800）でもクラッシュが継続

タブ文字を点字空白（U+2800）に置換しても、クラッシュが解消されませんでした。これは、点字空白自体がMeCabで問題を引き起こしている可能性を示唆しています。

### 2. 全角スペースを含むテストがすべてクラッシュ

全角スペース（`　`）を含むテストがすべてクラッシュしています。NFKD正規化でも全角スペースが半角スペースに変換されていない可能性があります。

### 3. 括弧文字を含むテストが多くクラッシュ

様々な括弧文字を含むテストがクラッシュしています。括弧文字の処理に問題がある可能性があります。

### 4. クラッシュ率が高い

0-100の範囲で36.5%のテストがクラッシュしています。これは深刻な問題です。

## 推奨される次のステップ

### 1. 全角スペースの処理を確認

NFKD正規化が全角スペースを半角スペースに変換しているか確認し、変換されていない場合は明示的に変換する必要があります。

```python
# text2mecab.py
txt = txt.replace("　", " ")  # 全角スペースを半角スペースに明示的に変換
```

### 2. タブ文字の分割処理を実装

タブ文字で入力を分割し、各セグメントを個別にMeCabで処理する方法を検討：

```python
# translator2.py
if "\t" in text:
    parts = text.split("\t")
    results = []
    for part in parts:
        if part:
            # MeCab処理
            ...
        # タブ位置に点字空白を挿入
        results.append(U+2800)
```

### 3. 括弧文字の処理を調査

括弧文字を含むテストがクラッシュする原因を調査する必要があります。

### 4. より広範囲なテスト

0-100の範囲だけでなく、全テストケース（2362件）を調査して、クラッシュパターンを完全に把握する必要があります。
