## 2. 失敗から学んだこと：betajp-251206ブランチの教訓（2分）

### 何が起きたか

- **betajp-251206ブランチ**: Python 3.13 x64対応を一気に進めようとした実験ブランチ
- **問題**: テストが失敗したまま（JP Brailleテスト、System Testsのタイムアウト）マージを進めてしまった
- **結果**: ブランチが不安定な状態になり、安定版リリースに影響を与えるリスクが発生

### 失敗の原因分析

1. **大きなPR単位**: 複数の変更を一度にマージしようとした
2. **段階的検証の不足**: 各段階でテスト通過を確認せずに次の段階に進んだ
3. **完了の定義が不明確**: テストが失敗していても「ほぼ完了」と判断してしまった
4. **開発環境の整備不足**: ローカル環境で問題を早期発見できなかった
5. **CIへの過度な依存**: ローカル環境での検証が不十分だった

### 教訓：品質保証の原則

1. **小さなPR単位で進める**: 各PRで必ず全テストが通過することを確認
2. **段階的な検証を必須とする**: 各段階でビルド・型チェック・単体テスト・システムテストを通過確認
3. **完了の定義を明確化**: テストが全て通過し、CIが安定して緑になるまで「完了」としない
4. **問題が発生したら即座に停止**: テスト失敗や不安定な動作が見られたら、次の段階に進まずに問題を解決
5. **開発環境の事前整備を優先**: 特にMeCabのユニットテストをローカルで頻繁に実行できる環境を事前に整備

## 3. 成功したアプローチ：段階的開発と具体的な成果（5分）

### 基本方針

**「2025.3.xjp安定版リリースを維持しながら、段階的に基盤を整備する」**

- 安定版リリースに影響を与えない範囲で実施
- 小さなPR単位で進め、各PRで全テスト通過を確認
- ローカル環境での開発効率を向上させる
- 将来のx64対応を見据えた検証環境を構築

### ステージ1：基盤整備とリファクタリング（完了）

#### 1.1 開発環境の整備（最優先）✅

- **目的**: CIに頼らず即時フィードバックを得られるテストループを確立
- **成果**: Python 3.11 x86 で MeCab / JP Braille を `jptools/runJpSmokeTests.ps1` から実行できるローカル環境を整備
- **効果**: 問題を早期発見し、修正サイクルを短縮

#### 1.2 DLLパス構造の統一 ✅

- **目的**: x86/x64の両方でDLLを正しくビルド・配置できる構造を作る
- **成果**:
  - x86 DLL: `miscDepsJp/include/python-jtalk/x86/(libopenjtalk|libmecab).dll`
  - x64 DLL: `miscDepsJp/include/python-jtalk/x64/(libopenjtalk|libmecab).dll`
  - `scons.bat jtalkSync TARGET_ARCH=x86`（または x64）で切り替え可能
- **効果**: アーキテクチャ別のビルドが独立して実行可能に

#### 1.3 libmecab.dllのソースビルド化 ✅

- **目的**: バイナリDLLを排除し、ソースビルドへ移行
- **成果**: x86でソースビルドに移行済み。リポジトリに長く存在していたバイナリDLLを削除
- **効果**: ビルドの再現性が向上し、x64対応時の作業が容易に

#### 1.4 overlay処理の廃止 ✅

- **目的**: ビルドプロセスを簡素化し、本家版との差分を最小化
- **成果**:
  - Phase 1: Pythonファイルと話者モデルを `source/synthDrivers/jtalk` に移動
  - Phase 2: `miscDepsJp/source` の全ファイルを `source/` に移動し、overlay処理を完全に廃止
- **効果**: ビルドプロセスが大幅に簡素化。`scons -c` で削除されるファイルは `source/` に直接配置されたファイルのみ

### ステージ2：ローカル開発環境でのマトリクス実行整備（完了）

#### 2.1 ローカル環境でのx86/x64マトリクス実行の実現 ✅

- **目的**: ローカル開発環境でjpSmokeTestをx86/x64マトリクス実行できて成功する状態を作る
- **成果**:
  - `checkJtalkArch.ps1 -Architecture x86 -RunSmokeTests` で x86 smoke テストが成功
  - `checkJtalkArch.ps1 -Architecture x64 -RunSmokeTests` で x64 smoke テストが成功
  - `.venv` を使用（x64 Python 3.13、x86 ビルドはサポートされていません）

#### 2.2 x64でのaccess violationエラーの修正 ✅

- **問題**: x64 での smoke テスト実行時に `access violation` エラーが発生
- **原因**: ctypes のポインタ型指定不足
  - x64 ではポインタが 8 バイトだが、ctypes のデフォルト型（`c_int` は 4 バイト）では正しく読み取れない
- **修正**:
  1. NULL ポインタチェックの追加
  2. `mecab_new.restype = c_void_p` - 戻り値のポインタ型を明示（8 バイト）
  3. `mecab_strerror.argtypes = [c_void_p]` - 引数のポインタ型を明示
  4. `mecab_sparse_tonode.argtypes = [c_void_p, c_char_p]` - 引数のポインタ型を明示
- **効果**: 過去に発生していた可能性のある問題を安全に再現可能な状態で修正

##### 2.2.1 access violationエラーの発見から原因特定までの調査プロセス

**ステップ1: 問題の発見**

- **状況**: x86 での smoke テストは成功していたが、x64 での smoke テスト実行時に `access violation` エラーが発生
- **エラーメッセージ**:

  ```
  Windows fatal exception: access violation reading 0x00000000BAAF17C0
  ```

- **エラー発生箇所**:
  - `mecab.py:173`: `libmc.mecab_strerror(mecab)` - `mecab` が NULL の場合に発生
  - `mecab.py:184`: `libmc.mecab_sparse_tonode(mecab, src)` - MeCab 解析時に発生
- **最初の仮説**: アーキテクチャ不一致（x64 DLL が x86 Python でロードされている）を疑う
- **確認**: `checkJtalkArch.ps1` で dumpbin 検証 → x64 DLL が正しくビルド・配置されていることを確認（アーキテクチャ不一致ではない）

**ステップ2: NULL ポインタチェックの追加**

- **仮説**: `mecab` が NULL の場合に `mecab_strerror` を呼び出すと `access violation` が発生している
- **対策**: NULL ポインタチェックを追加

  ```python
  if not mecab:
      logwrite_("mecab_new failed.")
      return
  ```

- **結果**: エラーが `access violation` から `OverflowError: int too long to convert` に変化
- **気づき**: エラーの種類が変わった → ポインタの扱いに問題がある可能性

**ステップ3: エラーメッセージからの原因特定**

- **新しいエラーメッセージ**: `OverflowError: int too long to convert`
- **分析**:
  - x64 ではポインタが 8 バイト（64ビット）
  - `ctypes` のデフォルト型（`c_int`）は 4 バイト（32ビット）
  - 8 バイトのポインタを 4 バイトの整数に変換しようとしてオーバーフローが発生
- **原因の特定**: `mecab_new` の戻り値が `c_void_p`（8 バイト）として明示されていないため、デフォルトの `c_int`（4 バイト）として扱われている

**ステップ4: 戻り値の型を明示**

- **修正**: `mecab_new.restype` を `c_void_p` に設定

  ```python
  libmc.mecab_new.restype = c_void_p  # x64 requires explicit pointer type (8 bytes)
  ```

- **結果**: エラーが `OverflowError` に変化（まだ完全には解決していない）
- **気づき**: 戻り値だけでなく、引数にも問題がある可能性

**ステップ5: 引数の型も明示**

- **仮説**: `mecab_strerror` と `mecab_sparse_tonode` の引数（`mecab` ポインタ）も正しく型指定されていない
- **修正**: `argtypes` を明示的に設定

  ```python
  libmc.mecab_strerror.argtypes = [c_void_p]
  libmc.mecab_sparse_tonode.argtypes = [c_void_p, c_char_p]
  ```

- **結果**: x64 での smoke テストが正常に完了することを確認

**ステップ6: 根本原因の理解**

- **x86 vs x64 の違い**:
  - **x86**: ポインタが 4 バイト（32ビット）→ `c_int` で扱える
  - **x64**: ポインタが 8 バイト（64ビット）→ `c_void_p` で明示する必要がある
- **ctypes のデフォルト動作**:
  - `restype` が指定されていない場合、デフォルトで `c_int` が使用される
  - `argtypes` が指定されていない場合、引数の型が推測されるが、ポインタ型は正しく推測されない場合がある
- **x64 での注意点**: ポインタ型は常に明示的に指定する必要がある

**調査プロセスの教訓**

1. **エラーメッセージの変化に注目**: `access violation` → `OverflowError` の変化が、問題の本質を示していた
2. **段階的な修正と検証**: NULL ポインタチェック → 戻り値の型指定 → 引数の型指定と、段階的に修正することで原因を特定
3. **アーキテクチャの違いを意識**: x86 では動作していたコードが x64 で失敗する場合、ポインタサイズの違いを疑う
4. **ctypes の型指定の重要性**: x64 環境では、ポインタ型を明示的に指定することが必須

#### 2.3 CI統合 ✅

- **x86 CI統合**: `testAndPublish.yml` で `jpSmokeTests` ジョブが `allTestsPass` 必須チェックに含まれている
- **x64 CI統合**: `.github/workflows/checkJtalkArch-x64.yml` を作成（独立した workflow）
  - x64 のみを実行し、x86 の CI に影響を与えない設計
  - `pull_request` トリガーを有効化し、PRで自動実行
  - CI環境でのコードページ設定問題を解決（コードページ932を設定）

##### 2.3.1 コードページ問題の発見から原因特定までの調査プロセス

**ステップ1: 問題の発見**

- **状況**: ローカル環境（x86/x64）ではjpSmokeTestが成功していたが、CI環境でx64 smoke testが `access violation` でクラッシュ
- **最初の仮説**: null terminate（文字列の終端処理）の問題を疑う
  - ctypesでC関数を呼び出す際、文字列のnull終端が正しく処理されていない可能性
  - `c_char_p` の変換や文字列の終端処理を確認

**ステップ2: ログからの発見 - ゼロ幅空白の問題**

- **mecab_debug.logの確認**: CI環境で生成されたログファイルを詳細に確認
- **発見**: ログにゼロ幅空白（U+200B, ZERO WIDTH SPACE）に関連する問題が記録されている
- **重要な発見**: ゼロ幅空白（U+200B）はテキスト解析の途中でマーカーとして使用されていた
  - `translator2.py` で `TAB_CODE = chr(0x200B)` として定義
  - タブ文字を `TAB_CODE`（ゼロ幅空白）に置換して、MeCab解析後に `TAB_CODE in mo.nhyouki` でチェック
  - テキスト解析の途中でマーカーとして機能しているため、すぐには排除できない
- **気づき**: 過去の失敗を思い出す
  - `tab_character_analysis.md` に記載されていた過去の調査結果を思い出す
  - 試行1で U+200B (ZERO WIDTH SPACE) を使用したが、MeCabがクラッシュした
  - 理由: UTF-8専用文字であり、`CHARSET_SHIFT_JIS` でコンパイルされたMeCabでは扱えない
  - この過去の失敗が、文字コード（コードページ）の問題を疑うきっかけになった
  - ゼロ幅空白がマーカーとして使われている以上、コードページの問題が根本原因である可能性が高い

**ステップ3: 文字コード（コードページ）を疑う**

- **仮説**: 過去のU+200Bの問題と同様に、文字コードの不一致が原因ではないか
- **環境の違いをリストアップ**:
  - OSバージョン（両方ともWindows）
  - Pythonバージョン（両方とも3.11）
  - DLLのアーキテクチャ（両方ともx64）
  - **ロケール設定・コードページ（未確認）** ← ここに注目

**ステップ4: コードページの違いを確認**

- **mecab_debug.logの再確認**: コードページ情報を確認
- **発見**: `mecab_debug.log` に `code_page=1252` が記録されている
- **ローカル環境との比較**: ローカル環境では `code_page=932` が記録されている
- **確認**: `chcp` コマンドでコードページを確認
  - **CI環境**: コードページ1252 (英語ロケール、Windows-1252)
  - **ローカル環境**: コードページ932 (日本語ロケール、Shift-JIS)
- **気づき**: コードページが異なる！
- **MeCabの前提条件を確認**: MeCabは `CHARSET_SHIFT_JIS` でコンパイルされている
  - ソースコード: `miscDepsJp/include/python-jtalk/lib/Makefile.mak` で `/D CHARSET_SHIFT_JIS` を確認
  - MeCabのドキュメント: Shift-JISでコンパイルされたMeCabは、コードページ932での動作が前提
- **重要な発見**: ゼロ幅空白（U+200B）がMeCab解析結果に含まれている
  - `translator2.py`の1366行目で`if TAB_CODE in mo.nhyouki:`とチェックしている
  - これは、MeCabが`CHARSET_SHIFT_JIS`でコンパイルされているにもかかわらず、UTF-8専用文字であるゼロ幅空白を処理できていたことを示している
  - 詳細は `projectDocs/jp/tab_character_analysis.md` の「CI環境でのコードページ設定問題」セクションを参照

**ステップ5: 原因の特定**

- **仮説**: コードページ1252の環境では、MeCabの内部処理（文字列処理、メモリアクセス）で不整合が発生し、`access violation` が発生している
- **検証**:
  1. CI環境でコードページ932を設定して再実行
  2. `mecab_debug.log` に `code_page=932` が記録されることを確認
  3. x64 smoke testが正常に完了することを確認
- **結論**: コードページの不一致が原因であることを確定

**ステップ6: 根本原因の理解**

- **MeCabの文字セット処理**: `CHARSET_SHIFT_JIS` でコンパイルされたMeCabは、Shift-JIS文字列を前提としてメモリ上で処理する
- **コードページの影響**: Windowsのコードページは、コンソール出力だけでなく、文字列の内部表現にも影響する
- **x64での影響**: x64環境では、ポインタサイズが8バイトになり、メモリアクセスのパターンが変わるため、コードページの不一致による影響がより顕著に現れる可能性がある

**調査プロセスの教訓**

1. **ローカルとCIの環境差を常に意識**: 同じコードがローカルで成功しCIで失敗する場合、環境の違いを疑う
2. **デバッグログの重要性**: `mecab_debug.log` にコードページ情報を記録していたことで、原因特定が容易になった
3. **段階的な仮説検証**: コード側の問題 → 環境の問題 → コードページの問題と、段階的に絞り込む
4. **前提条件の確認**: MeCabのコンパイルオプション（`CHARSET_SHIFT_JIS`）を確認することで、必要な環境条件が明確になった

### 成功のポイント

2. **ローカル環境の整備**: CIに依存せずに問題を特定・修正できる環境を構築
